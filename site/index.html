Open source · Apache-2.0 · Go · pre-1.0 prototype

One log. One binary.
One API.

KV, streams, documents, vectors and transactions are lenses over a single append-only log on object storage or a local disk. Branch it, rewind it, and provably forget a user, from one Go binary with no other services.

Pre-1.0 prototype — not for production. The core is model-checked and simulation-tested. Compaction, the HNSW index, auth/TLS and push consumers are new; larger-than-RAM state, a persisted ANN index and KMS clients are not done yet. Latest release: v0.1.0; this page describes unreleased main.

One transaction for everything

Consume a message, write the result and ack it atomically. Exactly-once processing with no outbox and no 2PC.

Branch, rewind, time travel

A branch is "parent log + LSN", so no data is copied. Undo a bad agent run, try a plan on a branch, or read any key as of any LSN.

Provable deletion

Shredding destroys a subject's key, so its data is unreadable on every lens, branch and point in history. You get a signed certificate, and the hash chain still verifies.

Simple to run

A single static Go binary with no CGO. One URL: ./data or s3://bucket/prefix. No ZooKeeper, no Raft, no brokers.

Fencing without clocks

Create-only writes (If-None-Match: *) plus epochs. A zombie writer can never commit after a new one opens.

Correctness you can rerun

TLA+ models checked by TLC, a deterministic fault-injecting simulator, property tests and kill -9 crash tests. All of them run in CI.

freshDB doesn't try to be the fastest at any one job. It tries to be the simplest thing that is good enough for small and medium apps and agents. Design principles, and what we refuse to build →

Install

One static binary (no CGO): CLI, HTTP server and the engine. Go 1.27+.

Latest main (journal storage, faster vectors, everything on this page):

go install github.com/raman20/freshdb/cmd/freshdb@main
freshdb version

Or build from source:

git clone https://github.com/raman20/freshdb
cd freshdb && go build ./cmd/freshdb

The v0.1.0 release has binaries for Linux, macOS and Windows on Releases (and is what @latest installs), but predates the changes since.

Same commands on S3 or MinIO: change the URL.

export FRESHDB_URL='s3://my-bucket/app1?endpoint=127.0.0.1:9000&insecure=1&create=1'
freshdb put hello world

Run the same engine as a JSON/HTTP server:

freshdb serve --listen 127.0.0.1:7070 &
curl -X PUT localhost:7070/v1/kv/k -d v
curl localhost:7070/v1/kv/k

Or embed it in Go:

db, _ := freshdb.Open(ctx, "./data")
db.Update(ctx, func(tx *freshdb.Tx) error {
  g := tx.Topic("tasks").Group("worker")
  msgs, _ := g.Fetch(1)
  tx.Put("result/1", out, freshdb.Subject("alice"))
  return g.Ack(msgs[0])   // atomic with the write
})

Better since v0.1.0

Durable single-client writes 12× faster (journal storage is now the default). Memory down from 7.1 to 1.55 GiB. No read-modify-write gives up any more. Exact vector search at 100k × 128-d: 19 → 1,051 QPS, recall 1.0. Durable publish: 119k msgs/s (NATS JetStream with SyncAlways: 8.5k). Opt-in HNSW: recall@10 0.988 at 3.3k QPS on 100k vectors (exact: 910). Push consumers: p99 at 1k msgs/s 1–15 ms vs 99 ms for a 100 ms poller.

Where it still loses

Memory vs Pebble: 1.55 vs 0.7 GiB peak, and ~1.5 vs ~0.09 GiB after Pebble’s bulk load (its data sits in the OS page cache). Point reads are below v0.1.0 (values now come from the log through a cache). Streaming p99 at 1k msgs/s is 3–43 ms across runs vs 1.9 ms for NATS. Badger commits more on one very hot key. HNSW at 1M vectors: recall@10 0.80 at ef 64, and the graph is rebuilt on every open.

How it works

Everything is the log. Lenses are pure folds over it, and object storage is the only coordination primitive.

Deterministic simulation

50,000 seeds, plus 10,000 on the final code. That run covered 137,293 acked transactions, 75,537 crashes, 29,979 writer takeovers and 114,926 injected storage faults, each checked against a reference model.

Property tests + crash tests

lens == fold(log) and DropSubject == fold(redacted) with rapid. 200 kill -9 rounds with 4 concurrent writers, and no acked write was lost.

Bugs found, then fixed

TLC found a stale-opener race that could brick the log. Fuzzing found non-canonical varints. The other tools found a vector lens state that wasn't canonical, and a late-landing DEK.

The specs are bounded and matched to the code by hand. That is evidence, not proof.

Honest limitations

A pre-1.0 prototype. Please don't put real personal data in it yet.

  • Keys, KV history, topics, documents and vectors live in RAM. Old versions are only dropped by freshdb compact / freshdb gc (new; GC keeps a configurable time-travel window), which keep every topic message; the journal file shrinks only offline (gc --shrink).
  • The opt-in HNSW vector index is rebuilt on every open (about 17 min at 1M vectors).
  • One writer per database, with no HA and no read replicas yet.
  • Only MinIO is tested. AWS S3 and R2 support the needed conditional writes but are untested.
  • The journal layout is new; its 8 MiB growth step stalls the commit path briefly.
  • The HTTP server has one shared bearer token and optional TLS; it binds to 127.0.0.1 by default.
  • In dev mode the KEK lives in the bucket. Backups taken before a shred can still decrypt that subject.
  • Keys and values without a subject are plaintext and are not covered by shred.
  • The on-storage format may change before 1.0.
