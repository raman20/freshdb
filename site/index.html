One log.
Every data model.

KV, streams, documents, vectors and transactions as lenses over a single object-storage-native log, with branching, rewind and provable deletion. One Go binary. One URL.

Pre-1.0 prototype — not for production. The core is model-checked and simulation-tested. Compaction, disk-backed lenses, auth/TLS and KMS keys are not done yet.

One transaction for everything

Consume a message, write the result and ack it atomically. Exactly-once processing with no outbox and no 2PC.

Branch, rewind, time travel

A branch is "parent log + LSN", so no data is copied. Undo a bad agent run, try a plan on a branch, or read any key as of any LSN.

Provable deletion

Shredding destroys a subject's key, so its data is unreadable on every lens, branch and point in history. You get a signed certificate, and the hash chain still verifies.

Simple to run

A single static Go binary with no CGO. One URL: ./data or s3://bucket/prefix. No ZooKeeper, no Raft, no brokers.

Fencing without clocks

Create-only writes (If-None-Match: *) plus epochs. A zombie writer can never commit after a new one opens.

Correctness you can rerun

TLA+ models checked by TLC, a deterministic fault-injecting simulator, property tests and kill -9 crash tests. All of them run in CI.

freshDB doesn't try to be the fastest at any one job. It tries to be the simplest thing that is good enough for small and medium apps and agents. Design principles, and what we refuse to build →

5-minute quickstart

Copy-paste. Outputs below are from a real run.

Install (Go 1.27+), or grab a binary from Releases:

go install github.com/raman20/freshdb/cmd/freshdb@latest

Try it on a local directory (default ./freshdb-data):

freshdb put greeting "hello"
freshdb put greeting "hello, world"
freshdb get greeting --at 1            # hello
freshdb pub events "signup: u17"
freshdb sub events --group mailer
freshdb branch create exp
freshdb put greeting "experimental" --branch exp
freshdb rewind main 1
freshdb put user/u17/email a@x.com --subject alice
freshdb shred alice
freshdb verify

Same commands on S3 or MinIO: just change the URL.

export FRESHDB_URL='s3://my-bucket/app1?endpoint=127.0.0.1:9000&insecure=1'
freshdb put hello world

Or run a server, which is the same engine over JSON/HTTP:

freshdb serve --listen 127.0.0.1:7070 &
curl -X PUT localhost:7070/v1/kv/k -d v
curl localhost:7070/v1/kv/k?at=1

Or embed it in Go:

db, _ := freshdb.Open(ctx, "s3://bucket/app1?endpoint=...")
db.Update(ctx, func(tx *freshdb.Tx) error {
  g := tx.Topic("tasks").Group("worker")
  msgs, _ := g.Fetch(1)
  tx.Put("result/1", out, freshdb.Subject("alice"))
  return g.Ack(msgs[0])   // atomic with the write
})

How it works

Everything is the log. Lenses are pure folds over it, and object storage is the only coordination primitive.

Correctness, shown rather than claimed

Every bounded model ran its full state space with no errors. CI reruns them, plus 2,000 simulator seeds, fuzzing and MinIO tests, on every push. spec/RESULTS.md

Deterministic simulation

50,000 seeds, plus 10,000 on the final code. That run covered 137,293 acked transactions, 75,537 crashes, 29,979 writer takeovers and 114,926 injected storage faults, each checked against a reference model.

Property tests + crash tests

lens == fold(log) and DropSubject == fold(redacted) with rapid. 200 kill -9 rounds with 4 concurrent writers, and no acked write was lost.

Bugs found, then fixed

TLC found a stale-opener race that could brick the log. Fuzzing found non-canonical varints. The other tools found a vector lens state that wasn't canonical, and a late-landing DEK.

The specs are bounded and matched to the code by hand. That is evidence, not proof.

Honest limitations

v0.1.0 is a prototype. Please don't put real personal data in it yet.

  • All lens state lives in RAM, with no compaction yet. Snapshots don't speed up open yet.
  • Vector search is exact brute force; there is no ANN index.
  • One writer per database, with no HA and no read replicas yet.
  • Only MinIO is tested. AWS S3 and R2 support the needed conditional writes but are untested.
  • The HTTP server has no auth or TLS (it binds to 127.0.0.1).
  • In dev mode the KEK lives in the bucket. Backups taken before a shred can still decrypt that subject.
  • Keys and values without a subject are plaintext and are not covered by shred.
  • The on-storage format may change before 1.0.
